System Architecture

Factory Inventory Management System

A three-tier demo application: a Vue 3 single-page client, a stateless FastAPI service, and an in-memory dataset loaded from JSON on disk. No database, no auth, no build pipeline beyond Vite — deliberately minimal so the data flow stays easy to trace.

Vue 3.4 · Vite 5 FastAPI · Pydantic 2 In-memory JSON Read-only API No auth · local dev only

Overview

Every screen is driven by four global filters — Time Period, Warehouse, Category, Order Status — held in a shared composable and forwarded as query parameters on every request. The backend never mutates or persists anything: it re-filters the same seven JSON files, held in memory since process start, on every call.

Request & data flow

Walking through what happens when a filter changes anywhere in the app:

  1. 1 Filter changes.

    A <select> in FilterBar.vue is v-model'd directly to singleton refs in useFilters.js — module-level state shared by every component that imports the composable.
  2. 2 View reacts.

    The active view has a watch() on all four filter refs; any change re-triggers loadData(), regardless of which component changed the filter.
  3. 3 Filters are translated.

    getCurrentFilters() maps UI state to API param names — warehouse, category, status, and month (only sent if not 'all').
  4. 4 Requests fire in parallel.

    api.js builds a URLSearchParams per call and issues several axios.get calls at once via Promise.all.
  5. 5 FastAPI filters in memory.

    The matching route calls apply_filters() and/or filter_by_month() over the lists mock_data.py loaded at startup — never mutating the originals.
  6. 6 Response is validated.

    Most routes declare a response_model (e.g. List[InventoryItem]), so Pydantic serializes and type-checks the payload before it leaves the server.
  7. 7 View stores the result.

    axios resolves, the view writes into a plain ref, and computed() properties re-derive automatically — no manual re-render logic.
  8. 8 Loading / error / data tri-state.

    Every view wraps this in the same try/catch/finally shape, toggling loading and error refs that gate what the template shows.

Notes & caveats

i

The backend is entirely read-only — no POST, PUT, PATCH, or DELETE route exists in main.py, despite a CreatePurchaseOrderRequest model being defined for one.

i

api.js calls /api/tasks and /api/purchase-orders, but neither route exists on the server. The task calls fail silently (caught and logged) — the Tasks UI still works because it also merges mock data from useAuth.js. createPurchaseOrder and getPurchaseOrderByBacklogItem are unused on the client.

i

purchase_orders.json ships empty, so has_purchase_order is false for every backlog item in this dataset.

i

Data loads once at process start. There's no persistence layer — restarting the server resets any in-memory state, and the dataset only changes via server/generate_data.py plus a restart.

i

CORS is wide open (allow_origins=["*"]) and there is no authentication layer — intentional for a local-only demo, called out explicitly in server/CLAUDE.md.
